## 2. 容器解析

早期用六个 RTXNTC 示例文件和一个 SponzaBricks 文件进行解析，日志结果为：

```text
7/7 files parsed successfully
```

这句话的含义是：七个 `.ntc` 的 Header、JSON 和 Data Chunk 能被 C# Reader 读取。它不代表七个 Sponza 材质，也不是质量分数。

当前 Reader 实际读取的 Header 是 40 字节：

```text
4 bytes   signature "NTEX"
4 bytes   containerVersion
8 bytes   jsonOffset
8 bytes   jsonSize
8 bytes   dataOffset
8 bytes   dataSize
```

过去文档把它写成 32 字节，是算术错误，已经更正。

## 4. Mask 通道权重

### Metalness

Flagpoles 金属遮罩在 16 bpp、loss scale 8 时发生明显塌缩：

```text
源图均值       201.84
解压后均值      27.46
```

将 Metalness loss scale 提升到 24，bpp 和文件大小不变：

```text
解压后均值     201.80
```

结论不是“所有材质都应该永远用 24”，而是：共享 bpp 预算会优先拟合信息量更大的通道，二值 mask 需要单独检查并调整 loss 权重。

### Smoothness

对 17 个已烘焙材质做源图与解压图的标准差比值比较，旧的 1x 权重下：

```text
Smoothness 平均约 0.94，最差 Ceiling 0.824
Color      约 0.999
Normal     约 0.98
AO         约 0.987
```

这说明 Smoothness 的细节/对比度损失更明显，因此 Bake Window 默认将其 loss scale 设为 16。更改权重后仍应重新测量，不要只凭肉眼判断。

## 5. 已验证的实现问题

### 5.1 latent 重复 BGRA swizzle

容器的 latent 是 BGRA4。Unity 侧没有直接使用原生 BGRA4，而是把四个 nibble 按物理顺序展开进 RGBA32。官方 shader 的 `.bgra` 用于补偿硬件 BGRA 格式；展开后继续照抄该 swizzle 会把 nibble 0 和 nibble 2 再交换一次。

修复：Unity 的 `NtcInference.hlsl` 和 `NtcDecompress.compute` 使用已经展开的 RGBA 值，不再做第二次 `.bgra`。

### 5.2 V 轴约定

磁盘导入纹理和 compute 直接写 RenderTexture 的行方向不同。不能翻 latent 采样或位置编码，因为两者与训练坐标是自洽的。

修复：在最终输出坐标/查询坐标处做转换，而不是在网络内部翻转。

### 5.3 TIFF 第四通道被 Pillow 隐藏

Photoshop 可能把 RGBA TIFF 的第 4 sample 标成 UNSPECIFIED。Pillow 因而只暴露 RGB，尽管 alpha 数据仍在 raw tile 中。结果是 MetallicGlossMap 的 A 通道或 BaseMap alpha 被静默跳过。

Bake Window 的转换代码检测 `RGBX/RGBXX` raw mode 并重解释为 RGBA。该实现使用 Pillow 的内部字段，升级 Pillow 后需要重新验证。

### 5.4 Smoothness semantic

源数据名为 Smoothness/Glossiness 时，manifest semantic 应为 `Glossiness`，不能写成 `Roughness`。当前 Unity 渲染按 texture name 匹配，所以旧标签不会改变本插件画面，但会误导按 semantic 消费数据的外部工具。

### 5.5 Alpha Cutout

Alpha 不是靠 Runtime 猜出来的。它必须在烘焙阶段从 BaseMap alpha 提取为独立 `AlphaMask`，随后由容器布局、compute 输出和材质 keyword 全链路传递。旧 `.ntc` 缺通道时必须重烤。

## 6. 显存数据的使用边界

早期原型有一组静态估算：

```text
latent + weights 约 16 MB
6 张 2048² 普通贴图约 96 MB
理论差值约 83%
```

这组估算描述的是“只保留 latent 和权重”的原型模型。当前默认 on-Sample 会额外分配 BaseColor、Normal、Mask 和 AO 的 capped RenderTexture cache，而且资源可能跨模式保留。因此这组数字不能当作当前插件的实测显存节省结论。

正确的现版本测量应至少统计：

- latent Texture2DArray；
- weight ComputeBuffer；
- on-Load 全分辨率 RenderTexture；
- on-Sample capped cache；
- mip 链；
- 切换模式后仍保留的资源；
- 原始材质贴图是否仍被 Unity 引用。

在完成这组采样前，README 不再给出节省百分比。
